Feature: **$ARGUMENTS**

> **Um assunto por janela:** esta janela é pra **esta** feature. Se, no meio dela, surgir um 2º assunto não relacionado, **não emende** — alerte, ofereça `/mss-spec:to-dolist adicionar <assunto>`, feche o escopo atual e abra **uma nova janela** pro outro assunto (ver a regra homônima no `CLAUDE.md`). É alerta, não trava.

Conduza no **nível de cerimônia atual** (padrão **médio**; troque com `/mss-spec:modo`). Os passos abaixo descrevem o nível **alto**; ajuste ao nível ativo:
- **médio**: design curto (poucas frases, sem doc de spec grande) + plano curto em tópicos + execução **inline** — sem subagentes nem dupla revisão. Ainda: OK antes de codar, TDD, verificação.
- **mínimo**: pule spec/plano; alinhe em 1-2 perguntas e vá direto ao código com TDD leve.
- **alto**: siga os passos como estão (spec doc + `writing-plans` + `subagent-driven-development`).

1. **Localize a spec do assunto**: procure em `docs/specs/` e no `docs/superpowers/INDEX.md` uma spec do mesmo assunto de **$ARGUMENTS**. Achou → você vai **atualizá-la** (reescrever "Estado atual" + acrescentar 1 linha no "Histórico"). Não achou → vai **criá-la**. Se o casamento de assunto for **ambíguo**, pergunte ao owner antes de decidir.
2. Invoque **superpowers:brainstorming** para esta feature: objetivo (1 frase), **Critérios de Aceite testáveis** (formato "DADO… QUANDO… ENTÃO…") e fora de escopo. **Espere o OK do owner** antes de qualquer código.
   - **Declare as premissas ANTES do OK — cada uma com a fonte.** Um bloco curto, em tópicos, com o que você está assumindo **sem ter sido dito**: framework/lib, infra, formato de saída, alcance da mudança ("só prosa", "só este comando"), profundidade esperada, "todo projeto tem X". **Antes de listar, passe no destilado** — `docs/superpowers/MAPA.md` → `docs/superpowers/INDEX.md` → `memory/MEMORY.md` (leia o gatilho de cada linha) → `docs/EVALS.md` (a falha já aconteceu?) → `CLAUDE.md`: se a resposta está lá, **não é premissa, é fato com fonte**. Formato de cada linha: `- <premissa> — fonte: <arquivo:âncora>` (ou `— fonte: você disse nesta sessão`) e, quando não houver de onde tirar, `- <premissa> — **sem fonte**`. **As `sem fonte` vêm primeiro** — são as que quebram. Se não houver premissa não-dita, diga isso em uma linha; **não invente** premissa pra preencher o bloco.
   - **Pedido com mais de um assunto: cubra cada um, explicitamente.** Se o pedido nomeia dois ou mais temas coordenados ("evals **e** context engineering", "importar **e** validar"), diga **qual peça serve cada um** antes do OK — e se algum ficou **sem peça**, declare isso em vez de deixar passar. Entregar uma metade e chamar de completo custa uma rodada inteira e faz o owner ter de apontar o buraco (caso **F-013**).
   - **Premissa derrubada pelo owner vira caso.** Anote na hora (o que você assumiu, o que era verdade); no fecho, o **`/mss-spec:memory capturar`** a transforma em caso de `docs/EVALS.md` (com guardrail e teste) e, se virar regra atemporal, em memória `feedback_*` com `gatilho:`. Restrição que o owner escreveu sobre o **meio** ("sem harness", "sem lib nova") **não** é medida de **profundidade** — se você leu assim, isso é uma premissa, e ela é `sem fonte` (caso **F-011**).
   - **Antes de desenhar do zero, cheque precedentes MSIG:** se a feature toca algo que outro projeto pode já ter resolvido (RAG/busca vetorial, extração de documento com LLM, conexão SQL Server/Postgres, deploy Azure, rede/proxy corporativo), rode **`/mss-spec:precedentes`** (ou invoque a skill `mss-spec:precedentes-msig`) e **abra o código real de lá** antes de replicar — reuso antes de reinventar. **Aquele projeto é SOMENTE-LEITURA**: você lê e traz o padrão pra cá; a âncora desta janela é **este** projeto e não migra (regra crítica 8 do `CLAUDE.md`). Mudança que seria lá → pare e mande abrir janela nova na raiz dele; bug visto lá → reporte, não conserte.
   - **Se a feature é tela/UI, decida o front AQUI (é decisão de design, muda o plano e os ACs):** consulte o **`docs/FRONTEND.md`** (design system MSIG) e escolha o nível **por tela** — página simples/institucional/formulário leve → **Nível 1 (Jinja + Tailwind)**; **tela densa** (grid com sort/filtro/busca, dashboard, muitos campos, date picker, seleção múltipla) → **Nível 2 (React + TypeScript + Mantine)**, e aí rode **`/mss-spec:frontend`** pra instalar o scaffold **antes** de construir a tela. Se o owner mandou "seguir o padrão do `/mss-spec:frontend`", é isto: o Nível 2. **`/mss-spec:frontend` existe** (`commands/frontend.md`) — não o declare inexistente por não estar na sua lista de invocáveis (é `disable-model-invocation`, como quase todo comando do kit): **leia o arquivo**. Se o projeto ainda não tem `docs/FRONTEND.md`, ele vem no `/mss-spec:kickoff`/`/mss-spec:upgrade`.
3. **Grave/atualize a spec viva** `docs/specs/<assunto>.md` (kebab-case pelo tema), com as seções fixas **Estado atual** + **Histórico**:
   - **alto**: o design completo do brainstorming (objetivo, Critérios de Aceite, decisões, fora de escopo) **é** o "Estado atual".
   - **médio**: "Estado atual" enxuto (2-4 frases) + fora de escopo em 1 linha.
   - **mínimo**: pule este passo (sem spec).
   - Ao **criar**, a 1ª linha do Histórico é `- <data> — criado: <resumo>.`; ao **atualizar**, reescreva o "Estado atual" e acrescente `- <data> — <o que mudou> (motivo: <por quê>).`. O "Estado atual" **sempre** reflete como o comportamento está HOJE (o git guarda o diff; o Histórico, a narrativa legível).
   - **Atualize o índice** `docs/superpowers/INDEX.md`: 1 linha, link **sempre** pra spec viva — `- [<assunto>](../specs/<assunto>.md) — <objetivo em 1 frase> — aberta`. (nível mínimo, sem spec: `- <assunto> — <objetivo> — aberta`, sem link.)
4. Invoque **superpowers:writing-plans**: quebre em tasks pequenas e ordenadas, cada uma cobrindo ≥1 Critério de Aceite por teste. O plano é **datado/efêmero** em `docs/superpowers/plans/` — não é a spec. **Se a feature mexe em banco/esquema**, a DDL vai pela disciplina do **`/mss-spec:banco`** (SQL **sempre** parametrizado; DDL versionada em `sql/NN_*.sql`, revisada pelo owner e **rodada FORA do app**; credenciais só via env) — não crie nem rode DDL pelo app.
5. Execute **uma task por vez** (superpowers:executing-plans / subagent-driven-development): TDD (teste do AC → vermelho → código → verde) e **rode e cole a saída** (verification-before-completion) antes da próxima. **Protocolo de log:** quando uma task for **gerar arquivos** e o projeto tiver o padrão de log montado (`config/logging.py`), antes de escrevê-los **liste os arquivos que vai criar com resumo de 1 linha cada** e **pergunte "logs em todos ou em quais?"** — instrumente com `logger = logging.getLogger(__name__)` só os escolhidos (regra de bolso: banco/API/regras de negócio sim, script simples não). Ver `/mss-spec:log`.
6. Ao concluir (**os "rode `/mss-spec:X`" abaixo são comandos `disable-model-invocation`: você os EXECUTA lendo o `commands/<x>.md` e fazendo os passos na mão — NÃO tente invocá-los via Skill, a invocação falha com "Falha ao executar a habilidade"**): `requesting-code-review` → **rode `/mss-spec:plano-teste`** (a suíte inteira; as validações desta feature dobram no baseline anti-regressão, que só é atualizado se passar 100%) → se a feature criou/alterou **rota ou endpoint** (ainda mais de **integração**, que outro sistema chama), revise contra `docs/SEGURANCA.md` (authz, entrada validada, `AUTH_TOKEN_ATIVO`/Bearer) — ou rode `/mss-spec:seguranca`. Confirme que o "Estado atual" da spec bate com o que foi entregue. Mude o status da linha no `INDEX.md` para `fechada`. **Atualize o `docs/superpowers/MAPA.md`**: o **Próximo passo** vira o que vem depois (próxima tarefa aberta do INDEX, ou "aguardando próxima feature"); e **se a feature criou/alterou uma integração com outro projeto** (a mesma rota/endpoint de integração revisada acima, ou um client pra outro serviço), registre/atualize a seção **Conexões** — do código real, nunca inventando (ou rode `/mss-spec:mapa`). **Capture a memória do assunto: rode `/mss-spec:memory capturar`** — ele destila a sessão em decisões (inclusive as **negativas**, o insumo anti-re-litígio "3 semanas depois"), grava o **diário de sessão** (`memory/sessions/<data>-<assunto>.md` + índice `memory/DIARIO.md`, foco nos **pivôs**) e roteia cada achado pro lar certo (aprendizado durável → `memory/` + `MEMORY.md`; decisão transversal → `docs/decisoes.md`; decisão de escopo "não fazer" → INDEX "Fora de escopo"; narrativa → Histórico da spec), aplicando `<private>` e **pedindo seu OK antes de gravar** — e ao final ele chama o `/mss-spec:mapa` (por isso a atualização do MAPA acima sai de graça). Só a **regra durável de sempre-ativo** ("Regras críticas" do `CLAUDE.md`) continua manual — é instrução, não memória. **Antes de integrar, rode `/mss-spec:release`** — o gate de pré-publicação que confere testes/versão/CHANGELOG/segurança/specs num veredito só; verde → `finishing-a-development-branch` (merge/PR).

**Git/branch:** **abra a branch da feature ANTES de codar, a partir da principal atualizada** (`git checkout <principal> && git checkout -b feature/<nome>`; `<principal>` = `main`/`master`) — nunca code direto na principal e **nunca ramifique de outra branch** (a feature sempre nasce da principal; ao integrar, volte pra ela). Para isolamento maior, use worktree (`superpowers:using-git-worktrees`). `git push` só quando o owner pedir. **Ao abrir a branch, atualize o `docs/superpowers/MAPA.md`** (seção **Onde estamos** = branch + assunto) — é o que a próxima janela lê na partida pra retomar.

Mudanças que **não** são feature (não precisam deste comando): **bugfix** → teste que reproduz o bug é a spec → corrige → verifica; **refactor** → gate é "testes verdes"; **chore/docs** → sem spec. **Porém**, se um bugfix/refactor **alterar o comportamento descrito numa spec existente** em `docs/specs/`, atualize o "Estado atual" dela + 1 linha no "Histórico" — senão a spec passa a mentir e induz o assistente a codar errado (reintroduzir o bug) numa tarefa futura.
